Solar OBD — Hardware & Firmware Reference

Interface contract between the ESP32 monitoring node and the Flutter app · generated from the current codebase

This document specifies everything the firmware side must provide for the app's diagnosis engine to work: the BLE service definition, the telemetry packet format, the physical quantities to sense, and the exact thresholds each reading is judged against. Every value here is taken from the live source in lib/services/ble_service.dart, lib/services/fault_diagnosis_service.dart and lib/models/system_config.dart.

1. System overview

The platform has two halves that share one system description. The sizing calculator designs an off-grid PV system and can save it (named) to the phone. The OBD-style monitor reads live telemetry from the ESP32 over BLE and diagnoses faults against thresholds derived from the selected saved system — so the hardware only has to stream raw measurements; all interpretation happens in the app.

[ Sensors ]      [ ESP32 ]              [ BLE / Nordic UART ]        [ Flutter app ]
 V, I, T   --->  read + build JSON  --->  notify on TX char  --->  parse -> SensorData
                 ~1 packet / 1-2 s                                 -> FaultDiagnosisService
                                                                    -> health score + fault codes

2. BLE contract

The app speaks the Nordic UART Service (NUS). The firmware must advertise this service and stream telemetry as notifications on the TX characteristic. The app is a pure consumer — it subscribes and listens; it does not write commands.

Advertised device namemust contain SolarOBD (e.g. SolarOBD-ESP32) — the scanner highlights matching devices
Service UUID (NUS)6e400001-b5a3-f393-e0a9-e50e24dcca9e
TX characteristic (notify → app)6e400003-b5a3-f393-e0a9-e50e24dcca9e
RX characteristic (optional, app → node)6e400002-b5a3-f393-e0a9-e50e24dcca9e — not used by the app today
Property required on TXNOTIFY, with a CCCD (0x2902) descriptor so the app can enable notifications
EncodingUTF-8 text, one JSON object per notification
The app buffers incoming chunks and extracts the last complete { … } object per burst, so a packet may span multiple BLE notifications — but sending one whole JSON object per notification is the reliable path and avoids fragmentation.

Connection flow the app performs

  • Scans (10 s) filtering on the NUS service UUID; falls back to an unfiltered scan if nothing matches.
  • Connects, discovers services, finds the TX characteristic, calls setNotifyValue(true).
  • On every notification: decode UTF-8 → parse JSON → build a SensorData reading → run diagnosis.

3. Telemetry packet format

Send a flat JSON object with these keys. Values may be integer or decimal. The app reads six fields; the timestamp is optional (the phone stamps its own arrival time).

JSON keyQuantityUnitTypical rangeNotes
v_panelPanel / array voltageV DC0 – ~90Array string voltage at the controller input
v_battBattery bus voltageV DC10 – 60At the battery terminals
currentArray / charge currentA DC0 – ~50Primary DC current; also used as a load proxy
t_panelPanel/module temperature°C15 – 90Back-of-module sensor
t_ambAmbient temperature°C20 – 45Shaded, away from the module
powerArray output powerW0 – array WpMeasured, or computed as v_panel × current
tsNode timestamp—optionalCurrently ignored; phone uses arrival time

Example packet

{"v_panel":72.4,"v_batt":26.1,"current":18.3,"t_panel":54.7,"t_amb":33.2,"power":1325.3}
Two temperatures are essential, not optional. The engine has no light sensor — it infers "is it daytime?" and "is irradiance strong enough to judge performance?" purely from how far t_panel sits above t_amb. If the ambient sensor is missing or reads equal to the panel, daylight-only checks silently switch off.

Recommended cadence: one packet every 1–2 seconds. The engine debounces faults over 3 consecutive readings (see §7), so a steady, regular stream matters more than a fast one.

5. How each reading is interpreted (gates)

Before any fault is raised, the engine computes these gate conditions from the incoming packet and the selected system's thresholds:

Daytimet_panel > t_amb + 3 °C — thermal only, so a disconnected (0 V) but sun-warmed panel still counts as daytime
Controller regulatingv_batt > absorptionThreshold — when true, current & performance checks are suppressed (a full battery throttling is not a fault)
Strong irradiancet_panel > t_amb + 15 °C — only then is the performance ratio meaningful
Under heavy load|current| > 0.6 × arrayIsc — suppresses false deep-discharge readings during a heavy draw
Performance ratiopower ÷ (arrayRatedW × tempDerate(t_panel)) — temperature- and age-corrected

7. Health scoring & debounce

  • Debounce: a condition must hold for 3 consecutive packets before its code raises — one noisy ADC sample will not trip a fault. Send a steady stream.
  • Scoring: health starts at 100; the app subtracts the worst single fault per domain (panel, current, battery, temperature, performance), not the sum of every fault. Result clamped to 0–100.
  • Reconnect: the app resets debounce streaks when a fresh connection begins, so a stale streak never carries across devices.

These numbers move with the system the user selects on the Scanner tab. A 48 V bank, a different panel, or an older install all shift them automatically — which is exactly why the firmware should stream raw measurements only and leave thresholds to the app.

9. Firmware checklist

  • ☐ Advertise a name containing SolarOBD and the NUS service UUID.
  • ☐ Expose the TX characteristic with NOTIFY + CCCD.
  • ☐ Sample Vpanel, Vbatt, I, Tpanel, Tamb; compute power if not measured.
  • ☐ Emit one UTF-8 JSON object per notification, every 1–2 s.
  • ☐ Calibrate the two temperature sensors against each other at night (they should read within ~1 °C) — the daylight gate depends on it.
  • ☐ Keep current sign consistent; the app uses |current| for the load gate.
  • ☐ Verify with the app's Simulate (Demo Mode) first, then real BLE.
